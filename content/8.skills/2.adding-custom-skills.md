## Introduction

To add a skill, create a directory under `laraclaw/skills/` with a `SKILL.md` file inside. There is no registration step, no command to run, and no cache to clear.

## Creating a Skill

Pick a short, lowercase, hyphenated name for the skill. That becomes the directory name, and the directory name *is* the skill name:

```bash
mkdir -p laraclaw/skills/release-notes
touch laraclaw/skills/release-notes/SKILL.md
```

## Writing the Frontmatter

Only `description` matters:

```markdown
---
description: Generate user-facing release notes from a list of git commits.
---
```

Write it as an answer to *"when should I use this?"*, because that is literally the decision the agent makes with it. It is the only part of your skill the agent sees before choosing to load it, so a vague description means a skill that never fires.

| Description | Result |
|---|---|
| `Release notes skill` | Never picked up. It names the file, not the job. |
| `Formats text nicely` | Fires at random. Too broad to match anything in particular. |
| `Generate user-facing release notes from a list of git commits` | Fires when someone pastes commits and asks for release notes. |

A `name` key is ignored if you add one. Rename the directory to rename the skill.

> [!TIP]
> If a skill is not firing when you expect it to, the description is almost always the reason. Ask for it by name once (*"use the release-notes skill"*) to confirm the skill itself works, then go back and sharpen the description.

## Writing Effective Skill Bodies

The body is the prompt the agent follows when the skill runs:

- **Be specific about the output format.** *"Three bullet points"* beats *"a few"*. If you want Markdown headings, say so.
- **Show, don't just tell.** If your release notes have a particular structure, include a short example. Examples are worth more than rules.
- **Constrain length.** *"Keep each section under 100 words"* beats *"Be concise"*.
- **Name the audience.** *"Written for end users, not engineers"* shapes the tone the agent picks.

A complete release-notes skill:

```markdown
---
description: Generate user-facing release notes from a list of git commits.
---

You are writing release notes for the end users of a SaaS product. Take the
provided list of commits and produce notes following this structure:

## What's New
- Two to four bullet points covering user-visible features.

## Improvements
- Smaller enhancements, in 1-2 bullet points each.

## Bug Fixes
- A short list of fixes, each one sentence.

Rules:
- Skip purely internal commits (refactors, dependency updates, CI changes).
- Write in present tense ("Adds", "Fixes", "Improves").
- Don't mention commit hashes, ticket numbers, or branch names.
- If a section has no items, omit it entirely.
```

## Bundling Scripts and References

Anything else you put in the skill's folder comes along with it. When the agent loads the skill it is told the folder path and given the file list, so the body can point at them by name:

```
laraclaw/skills/release-notes/
  SKILL.md
  changelog-format.md
  scripts/collect-commits.sh
```

```markdown
---
description: Generate user-facing release notes from a list of git commits.
---

Run `scripts/collect-commits.sh` to gather the commits since the last tag, then
format them following the house style in `changelog-format.md`.
```

Only `SKILL.md` is read into context when the skill loads. The companions cost nothing until the agent goes and reads one, which makes this the right place for long reference material you do not want in every prompt.

## Testing a Skill

The fastest way to test a new skill is the [terminal connector](/connectors/terminal):

```bash
php artisan laraclaw:chat
```

Then ask:

> Use the release-notes skill on these commits: ...

Iterate on the skill body until the output looks right.
